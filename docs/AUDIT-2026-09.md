## 二、分维度审计（现状 → 问题 → 方案）

### A. 架构与边界
- **现状**：mem.py 单一权威 + 索引可重建；Web/MCP/backup 都 import mem；数据与代码分离；八模块闭环。
- **问题**：① `mem.py` 已 1000+ 行，候选治理/多角色评审/评分/转正混在核心引擎里，职责渐重；② server 进程是启动时代码快照，改引擎必须重启（已踩 3 次，靠纪律而非机制保证）。
- **方案**：P2 把"评审/治理"拆出 `review.py`、把"备份"独立为子模块；server 加 mem 模块 mtime 校验或 `/api/reload`（低成本根治快照坑）。

### B. 数据质量
- **现状**：71 条（procedure 52 / lesson 10 / fact 9），今日 AI 提炼 5 条真经验、归档 40+ 碎片；热层 20 人工精选。
- **问题**：① 热层 auto-fill 补足质量差（抽查 4/6 为已内化元笔记），已定"人工评审"但缺**定期轮换机制**；② 无"召回救火榜"，不知道哪些笔记真被复用。
- **方案**：P1 建 recall 命中日志（哪些笔记被召回/救了火）→ 反哺热层轮换；P2 热层月度评审纳入 MONTHLY-TEMPLATE。

### C. 正确性 / 可靠性（自动链路是最大风险）
- **现状**：自动链路 = 收割 → 候选 → 多角色评审 →（lesson 自动转正 / procedure 留人工）。
- **问题**：① **收割"成功配方"识别仍会误收单工具名**（Write/Read/TaskStop 不是配方），今天已归档一批但判定未根治；② 收割"失败后成功"判定有缺陷（"成功片段"实为错误栈，误判过 1 次）；③ 单一写者未落地：多宿主并发写同一数据集无锁（当前单机顺序写兜底）。
- **方案**：P0 收割识别加"工具名黑名单 + 命令复杂度下限"，过滤单工具调用；P1 失败后成功判定改为"成功输出不含错误栈特征"；P2 多宿主一致性（单一写者或文件锁）待多机场景触发。

### D. 性能与容量
- **现状**：notes 6ms / 候选 20-43ms / 检索基准 20/20（top1 均值 167）；索引 1.3MB。
- **问题**：① BM25 在 500 条内的质量**未验证**（假设 A2，200 条时复跑基准）；② 词面检索不理解同义词，长尾查询会漏。
- **方案**：P1 在 200 条时跑 `bench_search.py` 复跑对比基线；P2 量破千后引入向量（触发信号：top1 平均分持续偏低）。

### E. 安全与合规
- **现状**：笔记去敏（占位符/方法论层）+ README 涉密声明 + Git 私人仓库（远程仅 .memory 代码，数据零上传）+ 数据走 backup.py 云端。
- **问题**：① **A8 Git 远程决策未定**：当前 private 仓库可用，但"是否允许私有远程"未拍板；② backup 的 mail/remote 渠道涉密快照（含笔记全文）经第三方（SMTP/服务器）传输，**未做合规评估**；③ SMTP 密码仍在配置文件明文（已留 PMEM_SMTP_PASS 环境变量，但 UI 未强提示）。
- **方案**：P0 A8 决策（一句话拍板）；P1 mail 渠道默认关闭 + 涉密提示；SMTP 密码强制走环境变量。

### F. 可维护性 / 可测试性
- **现状**：check_all 35 项 + bench_verify 16 项 + bench_search 20 组 + test_recall；文档 10+ 份。
- **问题**：① **无前端 DOM 级测试**——今天的"白页/弹层错乱/按钮错跳"全凭人肉发现，是最高频缺陷源；② 新 API（/candidates/body、/backup/targets 等）未纳入 check_all 冒烟；③ 18 处内联 onclick 依赖全局函数，未来模块化会整体失效。
- **方案**：P1 引入轻量前端冒烟（Playwright 打开页面断言六视图可渲染、console 无报错），并入 check_all；P2 事件委托重构 + 新 API 补冒烟。

### G. 体验
- **现状**：备份极简（选位置即备份）、候选可看正文+一键流转、记忆倒序、自动刷新已就位。
- **问题**：① 统计页状态显示英文；② 转正笔记标题 slug 过长（中文转长串拼音）；③ 候选正文为纯文本 pre，无 Markdown 渲染。
- **方案**：P2 统一状态中文映射、标题 slug 截断、正文 Markdown 轻渲染。

### H. 可持续运营闭环
- **现状**：自动收割（每小时）+ 候选评审（多角色+人工）+ 月度回顾模板 + 备份自动同步。
- **问题**：① **闭环缺量化**：recall 命中/无命中无日志，"哪条记忆救过火"不可知；② 候选池随收割持续产出，purge 靠手动/定时未自动化。
- **方案**：P1 recall 日志埋点（救火榜）；候选 purge 纳入自动收割后的自动清理（评审否决项自动归档）。

## 四、失败边界与取舍（诚实声明）

1. **自动链路永远不追求"全自动入库"**：信噪比优先于便利，procedure 碎片永远留人工，只有 lesson 踩坑可自动转正——这是刻意取舍，不是缺陷。
2. **向量检索是后置项**：当前 71 条 BM25 够用，提前引入是过度设计。
3. **多机一致性是伪需求（当前单机）**：等真实多机场景再上单一写者，否则徒增复杂度。
4. **涉密是红线**：任何引入第三方（LLM 审核、mail 备份、远程仓库）的选项，都必须先过"涉密合规"再上线，默认保持本地。
