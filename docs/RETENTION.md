# 分层清理机制（Retention / GC）

## 结论先说

**不做定时滚动删除。** 推荐方案是「分层降级 + 汇总压缩 + 冷存打包」，默认只压缩不删：

- 记忆的价值分布极不均匀：600 条归档里真正有用的可能只有 5 条任务级经验，其余是一次性命令碎片。
  按时间一刀切删除，最先牺牲的恰恰是那些"很久没用但一用就救命"的条目。
- 文本很便宜。当前全部数据 < 5MB，压缩后 < 1MB。为了省这点空间承担不可逆的信息损失，不划算。
- 真正需要治理的不是"容量"，而是**信噪比**：让检索结果里少出现碎片、让上下文不被稀释。
  这是分层与状态机要解决的问题，不是删除能解决的。

## 分层与阈值

| 层 | 内容 | 清理触发 | 动作 | 可逆性 |
| --- | --- | --- | --- | --- |
| T0 | 热层视图（`MEMORY.md` 里的核心经验） | — | 只读视图，不清理 | — |
| T1 | 正式笔记 `notes/*/` | — | **永不自动删除**；只报告 suspect/superseded 待人工复核 | 状态可逆 |
| T2 | 候选池 `notes/candidates/` | ≥60 天未处理，或 ≥50 条 | 滚动移入 `archive/` | 可逆（文件仍在） |
| T3 | 归档区 `notes/candidates/archive/` | ≥180 天 / ≥1000 条 / ≥200MB（任一） | 写 `SUMMARY-YYYY-MM.md` 摘要 → 打包 `_cold/cold-YYYY-MM.zip` | `--prune` 才删原文 |
| T4 | 证据流 `events/*.jsonl` | ≥90 天 | gzip 压缩到 `events/archive/` | `--prune` 才删原文 |
| T5 | 索引 `index.json` | 每次写入 | 重建即可，无历史价值 | — |

三个触发维度是**或**关系：时间（新鲜度）、数量（信噪比）、容量（物理上限）。
数量触发时按"最老优先"清超出部分，保留最新 80% 可热查，而不是一刀切清光。

## 用法

```bash
python mem.py gc                   # 只体检，不动任何文件
python mem.py gc --apply           # 执行（只压缩不删）
python mem.py gc --apply --prune   # 连原文一起删
python mem.py gc --archive-max 400 # 自定义阈值（也可 --cand-days/--archive-days/--event-days）
```

Web「统计诊断」页底部有同一份**只读**体检报告（各层条数/容量/最老天数/受保护数 + 建议）。
破坏性操作刻意不放 Web 一键按钮——误点一次不可挽回。

## 对检索质量与性能的影响

| 层 | 检索影响 | 性能影响 |
| --- | --- | --- |
| T1 保留全部 | 无（本就只召回 active） | 索引随笔记数线性增长，千级条目 BM25 毫秒级 |
| T2 滚动归档 | 候选池变小 → 人工终审负担下降 | 候选扫描 O(n)，n 从百级降到十级 |
| T3 冷存打包 | **归档区本就不参与检索**（索引只收正式笔记与候选池），故零影响 | 目录 inode 减少，`ls`/glob 更快 |
| T3 摘要保留 | 摘要 Markdown 仍可被 `recall` 命中 → 冷存条目"查得到" | 可忽略 |
| T4 证据压缩 | 证据流不参与检索（只作溯源） | 2.5MB → 0.42MB（实测 16%） |

关键点：**归档区从设计上就不在检索范围内**，所以清理它对召回率没有任何损失——
这也是"先归档、后冷存"两阶段的意义：先移出检索路径，再考虑物理压缩。

## 重要信息的保障措施

1. **受保护条目**：frontmatter 含 `hot: true` / `keep: true` / `protect: true` / `pin: true` 的，
   任何层级都不清理。
2. **冷存前必写摘要**：`_summaries/SUMMARY-YYYY-MM.md` 保留每条的 id/类型/标题/创建日期，
   任务级条目额外保留「任务目标 + 最终方案」要点。压缩不等于失忆。
3. **默认只压缩不删**：删原文必须显式 `--prune`，且此时冷存包已生成。
4. **正式笔记永不自动删**：最坏情况只是状态降级（active → suspect/superseded），一条命令可改回。
5. **候选转正是严格方向**：只有多角色评审强共识（≥78 分且 ≥4 角色通过）才进正式笔记，
   自动转正的条目默认不进热层（热层保护），不会被"自动写进去又自动清掉"。

## 收益与风险权衡

| 收益 | 风险 | 缓解 |
| --- | --- | --- |
| 目录与候选池不再无限膨胀 | 误删关键经验 | 默认不删；保护标记；冷存包兜底 |
| 冷存后目录变小、操作变快 | 冷存后找不到 | 摘要保留检索入口，标注所在冷存包 |
| 信噪比提升（碎片不再混在池里） | 摘要丢失细节 | 任务级条目保留要点；原压缩包保留全文 |
| 证据流体积下降 84% | 溯源链断裂 | 压缩而非删除；`--prune` 才删 |

## 持续增长时如何保持稳定

- **索引**：随笔记数线性增长，但只在写入时重建。万级条目仍在毫秒级；若真到十万级，
  再引入倒排分片，不必现在付这个复杂度。
- **检索**：BM25 只在 active 笔记上跑；归档/冷存不参与，增长的是"不参与检索"的部分。
- **上下文**：热层有硬上限（默认 12 条 / 900 token 预算），与人设画像分离，
  记忆量增长不会挤爆每次会话的注入。
- **磁盘**：按当前速率（约 0.7MB/月归档 + 2.5MB/月证据），压缩后一年 < 10MB。
  T3/T4 阈值就是为这个上限设计的兜底。
- **退化路径**：真到数据量大到影响体验时，优先提高 `--archive-days` 与 `--archive-max`，
  而不是缩短它们——清理是最后手段，不是日常操作。

## 什么时候该真的清理

1. 归档区里出现大量**同源重复碎片**（同一命令签名换参数）——这时清的是噪音，不是记忆。
2. 某类笔记已被更好的版本整体替代（状态机里标 `superseded`），确认后再冷存。
3. 迁移/重装前做一次归档打包，属于整理而非清理。

除此之外，默认不清理。
